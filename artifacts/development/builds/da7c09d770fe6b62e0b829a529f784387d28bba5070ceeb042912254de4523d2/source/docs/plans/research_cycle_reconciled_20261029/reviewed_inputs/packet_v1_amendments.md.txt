# Proposed Amendment and Scope Classification

Status: **PROPOSED; EFFECTIVE ONLY THROUGH THE CONSOLIDATED APPROVAL.**

## A1. Synthetic Checker grant supplement

The admitted [PD-009 §3](../../decisions/principal_decision_009_genesis.md)
adds a provider-different-from-proposer requirement to the Checker grants.
CV1 §III.8 instead defines independence by separate authority, protected
standards and evidence the proposer cannot rewrite, and permits additional
provider/human conditions in grant content. PD-007 does not erase PD-009's
extra requirement. A deterministic Checker and researcher have no trained
model providers, so the proposed arrangement does **not** satisfy that extra
condition merely by using different executable names or algorithms.

Proposed replacement for that supplement, for this milestone's initial
`AU-CK-A` and `AU-CK-B` and their explicitly permitted test successors only:

> For the first research-cycle milestone, where the proposer is the Principal
> acting directly, or a pinned deterministic synthetic design, and the Checker
> uses only the pinned deterministic synthetic designs and tools in the
> admitted setup packet, no different-model-provider
> condition is imposed. Provider and model provenance must truthfully state
> that no trained model/provider is used. All CV1 §III.8 independence
> conditions, separate Checker funding, own-subject exclusions and immutable
> closure requirements remain mandatory. Separate OS identities, separate
> executables and independent recomputation are required by these grants.
> This exception does not permit real model access. A real-provider design,
> provider substitution, an unpinned tool, or a wider deployment requires a
> separately admitted grant/design change; the original provider-diversity
> supplement remains the default outside this bounded synthetic scope.

This is a **document-phase amendment to PD-009's future grant content**,
not an edit of its historical record. No such runtime grant exists yet. It
does not amend CV1, weaken CV1's three independence conditions, let a Checker
decide, or waive a startup Check. After genesis, an actual grant amendment
would require the ordinary checked successor-grant/fence path; this record
provides no reusable runtime shortcut.

Constitutional delta relative to CV1: `ΔO=0, ΔS=0, ΔA=0`. This classification
does **not** mean no permission changes: compared with PD-009's previously
specified grants, deterministic synthetic Checkers become eligible under the
narrow condition above. That changed eligibility is explicitly approved as
grant content, within CV1's already-existing Principal grant authority. No
new category of authority or interpretation of constitutional independence
is introduced.

Rejected alternatives: claim two synthetic program names are different
providers; ignore the supplement as redundant; add real provider calls merely
to satisfy it; remove the independent Check for startup. None is proposed.

## A2. Complete setup content and narrow initial tool permissions

The exact values in `setup.json` fill the outstanding admission parameters:
300,000 ms binding interval, exact expiry instants, complete source revisions,
grants, tools, caps, schedules, initial limits, design/provenance and methods.
They are proposed Principal grant/source/limit/method content, not new
constitutional defaults. The 600-unit pool, 100-unit lineage cap, 60/30-unit
Checker grants, seven-day reservation duration, ten Research Designs and
two Checker lineages are retained. The discovery allowance is 60 units
within the shared pool, not an additional grant.

The initial grants in this packet enable only the named tier-1 synthetic
calculators and Checker computations. PD-009/PD-010 described a bounded
synthetic provider at tier 2 in addition to local compute; that provider is
**not enabled by these first-cycle grants**. Approval explicitly accepts
this narrower initial tool set for this bounded milestone. It does not
complete, cancel or substitute for the broader provider/funding demonstration
in those records. Adding that provider later needs its exact checked grant
content. No tool acquires rights because an older plan mentioned it. This
is a further pre-genesis grant-content narrowing, not a change in the tier
definitions, billing guarantees or constitutional meaning.

The “2027-04-30” grant expiry date is completed as the exclusive instant
`2027-04-30T00:00:00.000Z`. This conservative explicit instant is approved
here, not inferred from the old date. Seven-day reservation expiry remains
independent of grant expiry; an expired grant cannot admit fresh work even
if a reservation's own expiry is later. Checker grants bind nothing and
carry an explicit `null` binding interval with that reason, not a zero value.

`SRC-E` remains an offline real-equity-close archive declaration and is not
relabelled synthetic. It is never retrieved or used as resolution evidence
in this milestone. `SRC-SYN` explicitly supplies synthetic material. No
real vendor, account or model provider is selected. The synthetic source
declaration and methods do not earn forward credit regardless of chronology.

## A3. Implementation details and scope clarifications

Linux host accounts, transport peer binding, Python/SQLite arrangement,
canonical serialization, clock backend and bounded tool algorithms are
ordinary implementation/profile choices. Hash encoding represents the exact
CV1 content fields and preserves opaque governed IDs; it does not replace
their identity rules. No agent receives the right to grant or change its
criteria. The clock backend implements the existing Evidence-boundary clock;
it creates no second evidentiary time authority.

The narrow Checker expands its **implemented coverage** to grants, initial
limits, Agent Designs, Theme registration and supported Hypothesis
registration. These classes were already in the plan and grant scope; this
adds no transition class. Unsupported content yields no approval and cannot
be made supported by a catch-all `PASS`.

The worked cycle's hypothesis is determined by the exact template in the
design artifact; all numeric example costs are now fixed by this packet.
The fixed synthetic source includes a genuine failure path and success
calculation, so no approval or result labels are inputs to the algorithm.

The consolidated approval authorizes implementing and locally verifying
the narrow command service and Linux isolation fixture. It does not authorize
cloud deployment, host-wide changes on an existing production machine,
network data/provider access, Paper Book, framework adapters, public release
or a license. OS provisioning is limited to an operator-owned disposable local
Linux host/VM; ordinary platform privilege prompts remain separate from
constitutional admission. No provisioner or test code is created now.

## A4. Explicit stop boundary

There is no proposed constitutional text amendment. If implementation finds
that a field or operation here requires changing an admitted identity,
meaning, caller right, source meaning or Transition class, it must stop and
name the exact conflict. The approval is not blanket authorization for a
nonzero delta. Administrative fixture controls cannot bypass runtime Check,
Decide, Apply, accounting or historical-read rules.
